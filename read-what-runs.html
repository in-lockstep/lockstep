You can read what will run

Configuration as code has exactly one real disadvantage over a manifest: you can read a YAML file, but you cannot read a dependency-injection container. This is the answer to that, and the project names it as such rather than pretending the disadvantage is not there.

what is bound, and what it will say to the model
$ in-lockstep ls

bindings
  Fix                    -> DiagnoseThenFix (singleton, explicit)
  Implement              -> TDD             (singleton, explicit)
  Test                   -> PytestTest      (singleton, explicit)
  Validate               -> RuffValidate    (singleton, explicit)

prompts  (what each AI binding composes; * = not the shipped prompt)
  DiagnoseThenFix    fix/fix-writer fix/reproducer
                     guardrails: baseline, fix/fixing
  TDD                implement/oneshot implement/tdd
                     guardrails: baseline, implement/implementing

middleware  (privileged tier runs outside this chain and is not listed)
  OtelMiddleware
  CostBudget
  ApprovalGate

models  (verb -> model; resolved per verb, overridable at the call)
  implement              anthropic:claude-opus-4-6
  triage                 local:qwen3-8b

One screen: which adapter serves each verb, which model each verb routes to, the middleware order, and which prompts each AI binding composes — with a star on any prompt that is not the shipped one.

The first thing I do on any new repo is figure out what actually runs. Here that's one command and about four seconds, instead of an afternoon of reading YAML and guessing which override won.

The same question, three depths

What is bound — ls

The resolved container, printed. Including the anomaly worth noticing: a verb that exists and is bound to nothing, which is the shape a typo takes now that verbs are open values.

What the model is told — show-prompt

Composed offline, off the bound adapter. That distinction was a real defect for a while: the command imported the shipped prompt maps and never loaded your module, so a team that had replaced a lens was shown the prompt they replaced — by the one command whose entire job is saying otherwise. --diff now shows what you changed against the shipped body.

What all of it amounts to — pack describe

A receipt derived from the configuration: every binding with the capabilities it declares, every prompt with its exact fragment order, the merged policy floor, model routes marked priced or unpriced, the hosts a run may dial, and what evidence exists. Canonical JSON with a digest over exactly what is printed, so it can be compared by recomputation.

# the fields, and what each is read off
capabilities   the bound object — the set ApprovalGate and the budget refusal key on
projection     the composed prompt, via PromptLayers.projection()
policy         the stack's own layers with their sources, and what they merged to
models[].priced  the same table doctor's DOC151 uses
corpus         files on disk, in this repository only — null when there are none

Nothing there asks anybody what their code does. It reads what the objects already declare, which is what makes it evidence rather than a description.

What it does not do

Reading the output is easy. Holding the model in your head is not.

The developer who ranked this first also raised the sharpest objection to the framework overall: the concept count is high and it lands on one person. Verbs and request types, capabilities, container tiers, the policy stack, prompt layers, strategies, packs versus standards, provenance classes, cassettes, egress modes, fifteen diagnostic codes and sixty gates — the extending guide alone runs to seven hundred lines.

His words: “on a team of eight, one of us becomes the lockstep person and the rest of us file tickets, which is the same failure mode as the Jenkins guy we already have.” ls makes the configuration legible in four seconds. It does not make the framework small.
