Standards and extensions that travel

Two things move between repositories, and they move by opposite rules. A standard installs itself, because the risk is a team forgetting it. An extension only offers itself, because it hands a model tools and spends money. Getting that asymmetry right is the whole design.

a pack, genuinely installed — offered, and doing nothing
$ uv add acme-review-prompts
$ in-lockstep pack ls

installed packs  (offered, not in force — bind one in .lockstep/lockstep.py)

                    it runs nothing)

  corpus      2 case(s) — 2 with checks a machine settles, 2 needing a judge

imports: none is derived by walking the AST of every .py the distribution ships, not promised by the pack's declared kind. Listing a stranger's pack runs no code it ships: discovery never calls the entry point.

My problem was never authoring the standard, it was the repo that never got the memo. Making it a dependency means the only way to not have it is to delete it from your lockfile, and that shows up in review.

Engineering Director

Standards that arrive as a package install and cannot be loosened downstream is the first credible answer I have seen to governing this across three hundred repositories without hiring people to police it.

VP of Engineering

The extension surfaces are subclassing, binding and entry points — language features, not a plugin DSL. And discovery never imports the thing being discovered, which is a distinction most plugin systems don't bother to make.

Open Source Engineer

Two entry-point groups, one difference

in_lockstep.standards      installing IS applying
  package ──▶ detect() ──▶ container        (plugin tier, tighten-only)

in_lockstep.extensions     installing only OFFERS
  package ──╳── container                   never binds itself
     └─────▶ a line in lockstep.py ─────▶ container

A standards package may only tighten — lower a ceiling, never raise one; union the denied tools; strictest scan wins — so applying it automatically is safe, and the real risk is a repository that never picked it up. It binds at plugin tier, so a repository's own line still wins, and overriding one thing costs one line rather than a fork.

An extension pack hands a model write and execute tools and pays for a model call, so its arrival is a diff somebody read. in-lockstep ls will not mention a pack until your module names it. That also preserves a property worth more than the convenience it costs: which strategy runs is never a string, so nothing a ticket carries can steer a run toward an approach with more reach.

Accepting one is a record, not a rewrite

add re-derives the receipt from the code that is installed, compares it with what you accepted before, and records the result at .lockstep/packs/<name>.json — commit that file; it is the acknowledgement. Then it prints the lines for you to paste. It never edits your lifecycle module, and it never installs anything.

A capability the pack did not previously hold is refused until --accept says otherwise, and doctor re-derives against the record afterwards, so an upgrade that widens what a pack may do fails a check instead of arriving quietly.

What it does not do

Visibility of removal, not impossibility

A repository can delete the line that contributes your standard, or drop the dependency. The framework says so in its own policy module rather than implying otherwise: a middleware chain cannot bound code that never calls into it, and enforcement that must survive a hostile repository owner lives in a required CI check and in provider billing limits, not in a library.

And five of the eight policy fields enforce nothing today. The Engineering Director's review found it: max_turns, deny_tools and scan_input reach the run; network, permissions and three credit fields are merged, printed, and read by nothing else — while the documentation was recommending one of them as an org floor. It is now recorded as an unmet gate and the docs say which three bite. That is the project's own “mechanism nobody invokes” failure, found in the place it most matters.

Nothing here had ever been installed from a real index until the day this page was written — and doing it for the first time surfaced a bug where an editable install could not be located at all.
