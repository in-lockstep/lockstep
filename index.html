Your best engineer gets great results from AI. Your newest one doesn't.

Right now, that difference is your AI strategy.

in-lockstep makes AI a standard part of your software lifecycle instead of a habit each developer invents. The same prompts, the same guardrails, the same rules about when a model is even the right tool — for every engineer and every repository. Every interaction gets recorded. And when you change a standard, you can test whether it actually helped instead of arguing about it.

$ uv tool install 'in-lockstep[anthropic]'
$ in-lockstep init

Open source, Apache-2.0. Runs on your laptop. The whole evaluation costs nothing — see getting started.

The problem

Nobody has figured out how to do this at scale.

Your engineers are already using AI all day. That part happened without you. What has not happened is any of the things that would make it an engineering practice rather than a collection of private habits.

Today

Everyone is prompting, and nobody is comparing

Each developer has their own prompts, their own sense of what context to paste in, their own instinct for when to trust the answer. Some are genuinely good at it. Some are still learning. The results vary exactly as much as you would expect, and nothing anywhere records which was which.

Today

The good habits stay in one person's head

When somebody works out a prompt that gets reliably useful reviews, it lives in their editor. It does not reach the other thirteen people on their team, and it certainly does not reach the other two hundred repositories.

Today

And you cannot improve what you never saw

The interaction happened in a terminal. The prompt is gone, the response is gone, and the only trace is a diff somebody may or may not have read carefully. Ask “are we getting better at this?” and there is nothing to point at — so the answer is a matter of opinion, and the loudest opinion wins.

The answer

Make it a process, not a personal skill.

Four moves. Each one is ordinary engineering practice, applied to the part of your work that quietly stopped having any.

Move one

Standardise what the model is told

The prompt, the guardrails, the context and the skills stop being personal habits and become part of your lifecycle — attached to the situation they belong to. A security review composes the security prompt, then your organisation's guardrails, then the review skills, in that order, in every repository. Implementing a ticket composes something different. Nobody assembles it by hand, and nobody has to remember.

what a security review is actually sent
$ in-lockstep show-prompt security --projection

guardrail:baseline              ← every AI call in the company gets this
guardrail:review/reviewing      ← every review gets this
guardrail:acme/house            ← your organisation's rule
body:review/security-reviewer   ← the prompt for this job
skill:review/review-format
skill:review/review-revision

Composed the same way every time, and printable offline before it ever runs. Guardrails come first — that is a property of the framework, not a convention somebody has to follow.

An organisation ships its standards as a package. Installing it applies it, so there is no line for a team to forget, and it can only tighten what a repository already had — a team can be stricter than the standard and never looser.

Move two

Standardise when a model is used at all

Half of the value is knowing where not to put one. Cherry-picking a commit is git cherry-pick. Running your tests is running your tests. Deciding whether a report is a bug or a feature request is judgement, and that is where a model earns its place.

Your lifecycle says which is which, in one readable file, and the same file says what happens when the deterministic path hits something it cannot handle — a backport replays a commit with plain git, and only asks a model about the paths that actually conflicted.

Why it matters: a model invited into a job that did not need one is cost, latency and risk you took on for nothing. That decision should be made once, by your organisation, not forty times a day by whoever is at the keyboard.
Move three

Capture the whole interaction, not just the outcome

Because the work happens in an issue or a pull request rather than on somebody's laptop, all of it is recorded. Every message and every tool result, turn by turn — written always, not only when something breaks, because the run cannot know yet whether it went wrong. Plus what it cost, what it decided, and who approved it.

The prompt itself does not need storing: it is composed from files in your repository, so show-prompt reproduces exactly what any run was sent, at any time, offline. Reconstructable beats archived — an archived prompt tells you what happened once, a reproducible one tells you what will happen next time.

one real run's record, from the ledger
workflow   fix/from-ticket        args      {"ticket": "#109"}
status     succeeded              approval  {"by": "labeled:tpouyer"}
tokens     3,013,462              cost_usd  9.62445

findings
  fix.staged                  wrote src/in_lockstep/ai/builtins.py
  fix.staged                  wrote tests/…/test_sandbox_fixtures.py
  injection.exfil_token_names ×11   ← the scanner, reading the ticket text

Nothing here depended on somebody remembering to paste a transcript into a ticket. The run wrote it because that is what a run does.

This is the part that makes everything after it possible. A recorded interaction is evidence you can go back to — and the raw material for the next move.

Move four

Test a change to the standard, instead of guessing

This is the one that changes how the work feels. Someone proposes a better guardrail. Today, in most organisations, that is a conversation — the loudest person wins and nobody finds out for six months.

Here, captured interactions become cases: an input, and what a good answer looks like. Change the prompt, run the cases, and read what moved. Some of it a machine settles on its own; the parts that need judgement are marked as needing judgement rather than quietly counted as wins.

the framework, reporting on itself
$ in-lockstep eval report

cases        27
decided      0
outstanding  27  (need a judge)
pass rate    n/a — nothing decided

A rubric nobody judged is outstanding, not passed.

Note what it refuses to do. A tool that will not print a pass rate it has not earned is a tool whose pass rates mean something when it does print them.

Where this is going: the loop closes when captured runs are harvested into cases automatically and a proposed prompt change arrives as a pull request carrying its own evidence. The capture and the measurement both ship today; the harvesting between them is the roadmap, and the project says so rather than implying otherwise.

Getting started

Four commands. No key, no account, no platform team.

Nothing here needs a credential or a purchase order. You can find out whether it fits in an afternoon.

  1. uv add in-lockstep One package. Nothing else to run, host or sign up for.
  2. in-lockstep init It reads your repository — test runner, linter, CI — and writes a lifecycle file that already fits it. Thirty lines, and they are yours to edit.
  3. in-lockstep ls Prints what will actually happen: which steps use a model, which do not, and exactly which prompts and guardrails each one composes.
  4. in-lockstep review --offline A real security review of a real pull request, replayed from a recording — under a second, billed $0.0000.
A new engineer runs it on their first morning and gets real findings back in under a second, without a key and without asking me for anything. That used to be a two-day errand.

A run failed and filed its own bug report. A person put a label on it. An agent fixed it and opened a pull request. A person merged it. Neither side did the other's job — which is where the name comes from.
