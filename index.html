What they kept coming back to

Six things, ordered by how many of the five raised them unprompted. Each has a page with the full quotes, the mechanism, and what it does not do.

4 of 5 raised it

It costs nothing to try

Cassettes replay at the model input/output seam, so a full agentic session runs offline, deterministically, with no key and no spend.

I got a working, auditable run out of it in under a minute with no API key and no vendor relationship.

Read the detail → 4 of 5 raised it

Claims that fail CI

The capability table is enforced in both directions. Controls that pass unit tests but run on no live path get their own status, and the project used it against itself nine times.

This is the first one with a category for controls that exist, pass their unit tests, and are called by nothing at runtime.

Read the detail → 3 of 5 raised it

The blast radius is designed

The job holding the model key cannot write. The model stages changes it never applies. A pull request stays a draft until its tests actually pass.

The write token and the model key are never in the same process, and the file that defines the guardrails is one the agent is forbidden to touch.

Read the detail → 3 of 5 raised it

Spend is refused, not reported

A run that cannot be priced does not start. Budgets merge to the lowest. The framework says plainly which ceiling a bug could still defeat.

It refuses to start a run it cannot price. That is the only version of a budget I have seen survive contact with an unattended trigger.

Read the detail → 3 of 5 raised it

You can read what will run

Config-as-code’s one real disadvantage is that a container is harder to read than a manifest. One command prints the resolved answer; another derives it as an audit artifact.

One command and about four seconds, instead of an afternoon of reading YAML and guessing which override won.

Read the detail → 3 of 5 raised it

Standards and extensions that travel

An org floor arrives as a dependency and can only tighten. An extension pack arrives as an offer and does nothing until a line you wrote puts it in force.

My problem was never authoring the standard, it was the repo that never got the memo.

What all five said next

They agreed on the objection more than they agreed on the praise, and a project whose pitch is honest accounting does not get to leave that off its own front page.

Bus factor one, and no judged evidence yet

One author, nine days, no outside adopter. Every reviewer raised it independently. The extension mechanism had never been installed from a real index until the day this page was written; GitLab support has never run a live pipeline.

The eval corpus is unjudged. The framework's own answer to “does this produce good output” is currently that it cannot tell you — and it says so rather than computing a number over an empty denominator:

the project's own report on itself
$ in-lockstep eval report

cases        27
decided      0
outstanding  27  (need a judge)
pass rate    n/a — nothing decided

A rubric nobody judged is outstanding, not passed.
The self-documented weakness reads as credibility, not risk, and it is the main reason I kept reading. That is a vendor that will not surprise me in an incident review, which is worth more than a vendor with better numbers.

VP of Engineering · on whether the honesty is an asset

What would change their minds is specific and written down: a judged corpus with a real pass rate, ninety days of ledger from a repository the author does not own, and a second maintainer with commit rights.
