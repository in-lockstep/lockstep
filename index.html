Getting started

Four commands. No key, no account, no platform team.

  1. uv add in-lockstep One distribution. Provider SDKs are extras, so a bare install pulls none of them.
  2. in-lockstep init It reads your repository first — test runner, linter, Makefile, CI host — and writes a lifecycle that already binds them. Thirty lines, and they are yours.
  3. in-lockstep ls The resolved answer to “what will actually run”: every binding, the middleware order, the model route per verb, and the prompts each one composes.
  4. in-lockstep review --offline A real security review of a real merged pull request, replayed from a shipped recording — deterministic, under a second, and billed $0.0000.
A new engineer runs review --offline on their first morning and gets real findings back in under a second, without a key and without asking me for anything. That used to be a two-day errand.

The idea

A pipeline you cannot read is a policy nobody agreed to.

Most delivery automation is a pile of YAML that no test covers, that nobody can run locally, and that quietly became the most important program in your company.

in-lockstep makes it a module. Your review policy is a Python file — so changing it is a pull request with blame, history and a rollback, rather than a ticket to a platform team. You extend a verb by subclassing. You override behaviour by rebinding. You compose cross-cutting concerns as middleware. Not because those are clever, but because they are language features, and reinventing each one in YAML produces a worse version of it.

And because it is a program, the agents inside it are subject to the same thing everyone else is: code that was reviewed.

The first time it refused my own changeset for silencing a test, I realised the tool was going to keep me out of the code review I did not want to be in.

Standards roll out. Agency does not.

An organisation's floor arrives as a dependency — installing it is applying it, so there is no import for a team to forget. It merges tighten-only: a repository can lower a ceiling and can never raise one. An extension pack works the opposite way: installing it only offers it, and nothing runs until a line in your own file says so.

Extending it

Language features, not a plugin DSL.

You extend a verb by subclassing. You install a prompt by binding it. You distribute either as an ordinary Python package. There is nothing new to learn because there is nothing new here — which is the point.

a strategy that forgot to declare what it holds
UndeclaredAgency: AcmeTDD subclasses AiStrategy, so it is handed write_file,
delete_file and run_script and it pays for a model call — but `capabilities`
omits ['executes_code', 'spends_budget', 'writes_files'].

ApprovalGate, the budget refusal and Retry all read that set off the bound
object, so an undeclared strategy is an ungated one. Either subclass a per-verb
base (ImplementStrategy, FixStrategy), which declares it for you, or write:

    capabilities: ClassVar[frozenset[Capability]] = AGENCY

Refused at class-creation time, before anything runs — because the three gates that would have been silently skipped all read the same declaration.

I wrote a three-line strategy subclass that omitted capabilities and it refused to define the class at all. The error named the four things I was actually holding and the base class that would have declared them for me.

A run failed and filed its own bug report. A person put a label on it. An agent fixed it, staged the change and opened a pull request. A person merged it. Neither side did the other's job — which is the entire thesis, and the reason for the name.
