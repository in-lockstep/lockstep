Governance

Publish your standards. Install them. Watch them hold.

Your organisation decides how AI is used in engineering — which guardrails, which ceilings, which tools an agent may never touch. That decision has to reach two hundred repositories, survive contact with two hundred teams, and still let those teams do their jobs.

in-lockstep does that as a Python package. You publish it, teams depend on it, and installing it is applying it. What a team changes afterwards, they change in a pull request — which is the part most governance tools get backwards.

Part one

A standard is one function and one line of metadata

There is no console to configure, no policy language to learn, and nothing to host. Your standards are a package your platform team maintains like any other library.

The package · 1 of 2

The function

One entry point, handed a small facade. This is the whole of Acme's organisation-wide floor:

acme_lockstep/__init__.py
from in_lockstep import Policy


def apply(std):
    std.contribute(
        Policy(
            name="acme-baseline",
            # strictest wins — nobody can soften it
            scan_input="block",
            # ceilings merge lowest — nobody can raise it
            max_turns=16,
            # denies union — nobody can subtract
            deny_tools=("run_script",),
        )
    )

That is a real file — it ships in this repository as examples/acme-standards, and everything on this page was produced by installing it.

The package · 2 of 2

The line that makes it discoverable

pyproject.toml
[project]
name = "acme-lockstep"
version = "1.0.0"
dependencies = ["in-lockstep"]

[project.entry-points."in_lockstep.standards"]
acme = "acme_lockstep:apply"

The name on the left orders application when several standards packages are installed. Organisation before team is 00-acme before 10-payments — stated in the name, where everyone can read it, rather than left to a dependency resolver nobody can.

Part two

It arrives by being a dependency

Installing it is applying it. There is no import to remember.

That is the whole distribution mechanism, and the reason for it is arithmetic. At two hundred repositories, a convention that has to be hand-imported is drift by another name: every repo that forgets the line runs without your standards, and nothing anywhere says so.

a team repository's pyproject.toml
dependencies = [
  "in-lockstep",
  "acme-lockstep",   # ← this line is the governance
]

Nothing else changes in the repository. The team's own lockstep.py stays theirs; the standards apply underneath it, before its first line runs.

And failure is loud. A standards package that cannot be loaded stops the run, by name — “its standards are NOT in force, and running without standards somebody installed is worse than stopping.” There is deliberately no environment variable that skips loading, because an env var is removal that nothing reviews.

Part three

What a standard can do — and what it cannot

A standards package is handed a small facade rather than the repository's lifecycle. It can raise the floor. It cannot take the building.

It can
  • Contribute policy: ceilings, denied tools, scan strictness, egress
  • Bind implementations — a cost table, a tracker adapter, a house strategy
  • Only ever tighten what a repository already had
It cannot
  • Touch the middleware chain, the budget, or the model routes
  • Bind at the repository's own tier — everything it binds is plugin
  • Loosen anything, in any direction, ever

Tighten-only is not a promise. It is the merge.

Guardrails are an append-only registry. There is no removal API, and the merge has one direction: ceilings take the lowest, denied tools union, the strictest scan setting wins, and a closed egress rule cannot be reopened.

So a team that wants more turns can ask, and it will not get them:

the payments team's lockstep.py, asking for more
lockstep.policy.contribute(
    Policy(name="payments-house", max_turns=50, scan_input="warn")
)

Legal, greppable, and completely ineffective in the direction they tried. Here is what the run actually gets:

$ in-lockstep ls

standards  (in_lockstep.standards entry points; applied before this module's own lines)
  acme  <- acme-lockstep 1.0.0

policy
  acme-baseline   <- plugin:acme
  payments-house  <- local
  = network=(unset) scan=block deny_tools=1

$ # and the resolved ceiling the invoker is handed:
max_turns  = 16     ← the org's, not the 50 that was asked for
scan_input = block  ← the org's, not the "warn" that was asked for

Real output, from a repository with that exact file. The team's layer is still listed, with its source — because a contribution that had no effect is worth seeing too.

The one thing sealing cannot be: bindings resolve repository-above-organisation by construction, so a container cannot express “a standard the repository may not replace”. That is why guardrails are a stack and not a slot. What the stack preserves is the direction of travel; what it does not claim is impossibility. Part five is about that distinction, because it is the whole design.

Part four

Teams still own their repository

A governance model everyone routes around is worse than none, because it is the same outcome plus a false sense of coverage. So a team can change essentially anything — and the standard still holds where it matters.

Extend · bindings

One line beats the organisation's

Standards bind at plugin tier. The repository binds at explicit, and explicit wins regardless of order. Overriding the org's choice of anything is one line, in a file under review.

.lockstep/lockstep.py
lockstep.bind(CostTable, our_own_table)   # beats plugin:acme's
Extend · prompts

Add a rule of your own, and see exactly what it did

plus() appends, so a house guardrail lands after the shipped baseline instead of displacing it. And the framework will show you the change to what the model is told, before anything runs and before anything is spent:

what one house rule did to the prompt
$ in-lockstep show-prompt security --diff

--- shipped/review/security
+++ AiReview/review/security
@@ -42,6 +42,10 @@
+<!-- guardrail: payments/actions -->
+Never approve a new `run:` step in a workflow without naming, in the
+finding, which secrets that step can read.

And ls keeps the score, so nobody has to remember which repositories have customised which prompts:

in-lockstep ls
prompts  (what each AI binding composes; * = not the shipped prompt)
  AiReview           review/intent review/performance review/security review/tests
                     guardrails: baseline, review/reviewing, payments/actions
Extend · strategies and verbs

Or replace how the work is done entirely

A team that wants red-then-green instead of one pass writes lockstep.use(TDD). A team that wants its own approach writes a strategy class and binds that. A team with a step nobody else has adds a verb. The walkthrough covers how a strategy works →

All of it still runs inside the standard. A house strategy that asks for forty turns under an organisation ceiling of sixteen gets sixteen. Extending the framework does not extend its permissions.

Part five

Enforcement is visibility, not prevention

A team can remove your standard. What they cannot do is remove it quietly.

This is the design decision the rest of the page rests on, and it is worth stating plainly rather than implying otherwise. in-lockstep does not try to make a repository unable to change its own configuration. It makes every such change a diff, in a pull request, in history, with a name on it.

Removing a standard

Is deleting a dependency

the pull request somebody has to open
--- a/pyproject.toml
+++ b/pyproject.toml
 dependencies = [
   "in-lockstep",
-  "acme-lockstep",
 ]

Reviewable, blameable, and searchable across every repository you own. Compare that with the alternative most tools ship: a setting in a console, changed by someone with the right role, leaving a log entry nobody reads.

Weakening a prompt

Is a diff the framework prints for you

Replacing the guardrail stack instead of appending to it is legal. It is also reported, on every prompt a bound adapter composes, by a command that needs no credential:

in-lockstep doctor
WARNING DOC171  review/security does not open with the shipped guardrail baseline
                 Its stack starts guardrail:payments/actions. Constructing a fresh
                 PromptLayers replaces the baseline; `plus()` appends and keeps it.
                 `in-lockstep show-prompt review/security --diff` shows the change.

A warning, never a refusal. Replacing the stack is a legitimate thing to do — and it is exactly the thing a reader of somebody else's repository most needs told.

The audit answer

“What is actually in force, in this repository, right now?”

Configuration as code has one honest disadvantage: you can read a YAML file, but you cannot read a container. ls is the answer to it — one command, no credential, no spend, printing what applied and where every layer came from.

And the config itself is loaded from a trusted ref. A pull request cannot supply the file that defines the controls constraining its own review. That one is not visibility — that one is prevention, and it is where prevention actually belongs.
Being straight about the limit

Where hard enforcement really lives

What a framework cannot do

A middleware chain cannot bound code that never calls into it. Nothing installed inside a repository can stop a determined owner of that repository — and any tool that tells you otherwise is selling you the feeling rather than the control.

Enforcement that must survive a hostile repository owner lives in two places you already have: required status checks on the branch, and spend limits at the provider. in-lockstep is built to make those two sufficient, by making everything else legible — so the check has something true to check, and the bill has a name attached.

That is the trade, stated once: you give up the fantasy of a configuration nobody can change, and you get an organisation where every change to it is a diff you can find, read and revert.

One package. Two hundred repositories. Every change visible.
