Governance

Write your rules once. Every team gets them.

Somebody in your company has to decide how AI gets used in engineering. Which rules it always follows. How much it may spend. What it is never allowed to touch.

The hard part is not deciding. It is making the decision reach two hundred teams, stay put, and still leave those teams free to do their jobs. Here, your rules are a small Python package. Teams add it to their project the way they add anything else, and it starts working.

Part one

Your rules are a small package

Nothing to host, no console to set up, no new language to learn. If your team can publish a library, you can publish your standards.

Step 1

Write the rules

One short function. This is all of Acme's — three rules that every repository in the company will follow:

acme_lockstep/__init__.py
from in_lockstep import Policy


def apply(std):
    std.contribute(
        Policy(
            name="acme-baseline",
            # strictest wins — nobody can soften it
            scan_input="block",
            # ceilings merge lowest — nobody can raise it
            max_turns=16,
            # denies union — nobody can subtract
            deny_tools=("run_script",),
        )
    )

A real file. It ships in this project as examples/acme-standards, and everything else on this page came from actually installing it.

Step 2

Add the line that says “these are rules”

An ordinary package description, plus one line telling lockstep where to find your function:

pyproject.toml
[project]
name = "acme-lockstep"
version = "1.0.0"
dependencies = ["in-lockstep"]

[project.entry-points."in_lockstep.standards"]
acme = "acme_lockstep:apply"

If you publish more than one set of rules — the company's, then a division's — the name decides which goes first. 00-acme before 10-payments, so the order is something anyone can read rather than something they have to work out.

Part two

Teams get them by adding one line

Installing it is turning it on.

There is no setup step afterwards and nothing for anyone to remember. That matters more than it sounds: across two hundred repositories, a rule that each team has to switch on is a rule most teams eventually do not have — and nobody finds out.

a team's project file
dependencies = [
  "in-lockstep",
  "acme-lockstep",   # ← this line is the governance
]

That is the whole thing. Nothing else in the repository changes.

And if it breaks, everything stops. If your rules package fails to load, the run halts and says so. It never quietly carries on without the rules somebody installed — and there is no switch to skip them, because a switch is a way to turn off your standards that leaves no trace.

Part three

Teams can be stricter. They cannot be looser.

Your rules set a floor. A team can always stand higher than it — and there is no way to dig underneath.

Your rules can
  • Set limits — spend, how long the AI may work, what it may never touch
  • Swap in company defaults, like your own pricing table or issue tracker
  • Only ever make things stricter than they already were
Your rules cannot
  • Decide a team's budget, or which model they use
  • Outrank a team's own choice when they make one deliberately
  • Loosen anything, in any direction, ever

Watch it hold

Rules never replace each other — they combine, and only in one direction. Two limits become the lower one. Two lists of banned tools become both lists. The stricter setting always wins.

So a team can ask for more room, and simply not get it. Here is a team asking to run the AI three times longer and to check its inputs less carefully:

a team's own file, asking for more
lockstep.policy.contribute(
    Policy(name="payments-house", max_turns=50, scan_input="warn")
)

Perfectly legal to write, and it does nothing in the direction they wanted. This is what the run actually gets:

$ in-lockstep ls

standards  (in_lockstep.standards entry points; applied before this module's own lines)
  acme  <- acme-lockstep 1.0.0

policy
  acme-baseline   <- plugin:acme
  payments-house  <- local
  = network=(unset) scan=block deny_tools=1

$ # and the resolved ceiling the invoker is handed:
max_turns  = 16     ← the org's, not the 50 that was asked for
scan_input = block  ← the org's, not the "warn" that was asked for

Real output. Notice their rule is still listed, and it says where it came from — a rule that had no effect is worth being able to see.

Part four

Everything else is still theirs

Rules that get in the way get worked around, and then you have the same problem plus the belief that you solved it. So teams keep real freedom — inside the floor you set.

They can swap a piece out

Their choice beats yours, when they make one on purpose

Your package sets the default. A team that deliberately picks something else writes one line, in a file that goes through review like any other code.

the team's own file
lockstep.bind(CostTable, our_own_table)   # beats plugin:acme's
They can add their own rule

And see exactly what it changed

A team adds a rule of its own and it lands after the company's, so yours stays underneath. Then the tool shows them precisely what they changed about the instructions the AI gets — before anything runs, before anything is spent:

what one team rule did to the instructions
$ in-lockstep show-prompt security --diff

--- shipped/review/security
+++ AiReview/review/security
@@ -42,6 +42,10 @@
+<!-- guardrail: payments/actions -->
+Never approve a new `run:` step in a workflow without naming, in the
+finding, which secrets that step can read.

And one command lists which repositories have added rules of their own, so nobody has to keep track by hand:

in-lockstep ls
prompts  (what each AI binding composes; * = not the shipped prompt)
  AiReview           review/intent review/performance review/security review/tests
                     guardrails: baseline, review/reviewing, payments/actions
They can change how the work is done

Or replace the approach entirely

A team that wants the AI to write a failing test first switches to that approach in one line. A team with its own way of working writes it and uses that. The walkthrough shows how →

And it all still runs inside your rules. A team's own approach that asks for forty steps, under a company limit of sixteen, gets sixteen. Building on the framework does not buy anyone extra permission.

Part five

Nobody can change it quietly

A team can remove your rules. What they cannot do is remove them without anyone noticing.

This is the part worth saying out loud, because most tools imply the opposite. in-lockstep does not try to make a repository unable to change its own setup. It makes every such change show up as a normal code change — a pull request, with a diff, with a name on it, kept in the history.

Dropping your rules

Means deleting a line, in a pull request

what somebody would have to open
--- a/pyproject.toml
+++ b/pyproject.toml
 dependencies = [
   "in-lockstep",
-  "acme-lockstep",
 ]

Reviewable, attributable, and searchable across every repository you own. Compare that with the usual alternative: a setting changed in a console by whoever had the right permission, leaving a log entry nobody reads.

Weakening the AI's instructions

Gets reported, by a command anyone can run

A team can drop the company's rules out of the AI's instructions rather than adding to them. That is allowed — and it is also announced, on every prompt, by a command that needs no password and costs nothing:

in-lockstep doctor
WARNING DOC171  review/security does not open with the shipped guardrail baseline
                 Its stack starts guardrail:payments/actions. Constructing a fresh
                 PromptLayers replaces the baseline; `plus()` appends and keeps it.
                 `in-lockstep show-prompt review/security --diff` shows the change.

A warning, never a refusal. Sometimes replacing the rules is the right call — and it is exactly the thing somebody reading that repository later needs told.

The question an auditor asks

“What is actually switched on in this repository, right now?”

One command answers it — no password, no cost — listing every rule in force and where each one came from. That is the answer to the one real drawback of keeping your setup in code: you can read a config file at a glance, and you cannot read a program.

And the setup is read from a trusted place. A pull request cannot supply the file that sets the rules for reviewing that same pull request. That one is not visibility — that one is genuinely prevented, and it is where prevention actually belongs.
The honest limit

Where real enforcement lives

What no framework can do

Nothing installed inside a repository can stop somebody who owns that repository. Any tool telling you otherwise is selling you the feeling of control rather than the control.

Enforcement that has to survive a determined owner lives in two places you already have: required checks before a branch can merge, and spending limits at your AI provider. in-lockstep is built to make those two enough — by making everything else easy to see, so the check has something real to check and the bill has a name on it.

That is the trade, in one sentence: you give up the fantasy of a setup nobody can change, and you get a company where every change to it is a diff you can find, read, and undo.

One package. Every repository. Every change visible.
