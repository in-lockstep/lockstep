The blast radius is designed

The developer's fear and the CISO's question turn out to be the same question asked at different volumes: when this goes wrong, what could it reach? The answer is arranged in three places, and none of them is the prompt.

the path guard, consulted at every point that writes
$ python -c "from in_lockstep.core.changes import ChangeGuard; ..."

.lockstep/lockstep.py              REFUSED  tier 1  rule .lockstep/
.github/workflows/lockstep.yml     REFUSED  tier 1  rule .github/
src/app.py                         allowed

The file that defines every binding, tool grant and protected path is itself the first entry in the deny list — so an agent cannot edit the file that constrains it. The rule is enforced at three separate write paths driven off one shared list.

It won't open a green-looking pull request it hasn't actually tested. If the suite fails it stays a draft or turns into an issue, which is exactly what I'd want a junior teammate to do.

Three separations, and why each one exists

The credential split

One process cannot hold two token scopes, so the work is two jobs. The job that talks to the model holds the provider credential and contents: read. The job that opens the change holds a write token and never sees the provider credential. That split is the reason the trampoline has two jobs at all — it is not ceremony, it is the only way to have both capabilities without having them together.

gate      →  implement            →  propose
(no key)     (provider key,          (write token,
              contents: read)         no provider key)

The model stages; it does not apply

A session writes into a ChangeSet and touches nothing on disk. Applying it is a separate step that runs the same path guard a second time, on the artifact. Locally that is two commands; in CI it is two jobs, and only the second can write.

A draft until the tests say otherwise

An AI-authored change opens as a draft pull request. It is marked ready only when the suite actually passed against the staged change — and if it did not, the run files a follow-up issue instead, bounded by max_attempts. The attempt counter lives in labels on the ticket, and doctor fails when those labels do not exist, because a host that silently drops an unknown label would leave every follow-up reading attempt zero and the cap bounding nothing.

What it does not do

The gate authorizes the asker, not the issue

Anyone who can see a repository can file an issue in it. When a member types /implement on a drive-by ticket, that body is handed to a model holding write tools. The framework's answer is not that this cannot happen — it is that the ticket stays classified untrusted, the writes are staged, the guard checks them twice, and the result arrives as a pull request a person reads.

The gate bounds who can spend money. It does not bound what the text says. That sentence is in the documentation, not paraphrased from it.

And the guard governs the write path, not a running process: a command from an allowlisted program could write anywhere the process can. That is why commands run in a throwaway worktree of HEAD, inside a container with no network, with every credential dropped from the environment — and why the framework refuses rather than silently falling back when no container runtime is present.
