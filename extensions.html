Extensions

Somebody already solved it. Borrow their work.

A team writes a really good security review for Django projects. Another team works out how to make the AI handle their database migrations properly. Right now that work stays where it was written.

A pack is that work, wrapped up so other people can use it. You publish one the way you publish any Python package. Other people find it, check what is in it, try it for free, and switch it on — and nothing happens to their project until they say so.

Part one

Making one

A pack is a normal package with one extra line. The example below is real — it ships in this project, and every command on this page was run against it.

Step 1

Put your work in a folder

This one is prose — a security review that knows about the company's database layer, and a rule about migrations. Just markdown files:

the whole package
acme-review-prompts/
├── pyproject.toml
└── acme_review_prompts/
    ├── __init__.py          a docstring, and nothing else
    ├── pack.toml            what kind of thing this is, in one line
    ├── prompts/
    │   ├── security.md      the review itself
    │   └── house.md         the rule about migrations
    └── corpus/              example cases, so people can measure it
Step 2

Say what it is

pack.toml
[pack]
kind = "prompt"
summary = "A security lens that knows about our ORM, and a guardrail about migrations"

That is the whole file, and it is deliberately almost empty. A pack cannot set your budget or pick your model here, because the moment a downloaded file can do that, downloading something has become a risk.

Step 3

Add the line that makes it findable, and publish

pyproject.toml
[project]
name = "acme-review-prompts"
version = "1.0.0"

[project.entry-points."in_lockstep.extensions"]
acme-review-prompts = "acme_review_prompts"

Then publish it wherever you already publish packages — your company's internal index, or the public one. There is nothing else to sign up for.

Part two

Finding one

A catalog is a plain text file in a git repository listing packs. That is the entire marketplace — no service, no accounts, no ranking anyone has to argue about.

Step 1

Point at a catalog

Your company publishes one for internal packs. Public ones work the same way. Adding it is one command, and it writes a file you commit like anything else:

registering a catalog
$ in-lockstep market add acme https://raw.githubusercontent.com/acme/index/main/index.toml

registered  acme  https://raw.githubusercontent.com/acme/index/main/index.toml
wrote       .lockstep/market.toml  — commit it

It must be an https address. A catalog says which code to install, so it is fetched over something nobody can tamper with along the way.

Step 2

Search it

in-lockstep search
$ in-lockstep search security

acme  (states entry criteria)
  acme-review-prompts   prompt   A security lens that knows about our ORM, and a
                                 guardrail about migrations
                                 <- 1 criterion/criteria unmet

Real output. Look at that last line: this catalog publishes standards its entries are supposed to meet, and it is telling you that this pack does not meet one of them. A listing you can check beats a listing you have to trust.

Part three

Checking it before you trust it

Installing a pack changes nothing about how your project runs.

This is the difference between a pack and your company's rules. Rules apply themselves the moment they are installed, because that is what rules are for. A pack from someone you do not know only ever offers. Until you write a line saying to use it, it sits there doing nothing.

What is in it?

One command reads it and tells you

Not what the author claimed — what the files actually contain. This is worked out on your machine, from the pack you downloaded:

in-lockstep pack describe
$ in-lockstep pack describe acme-review-prompts

pack          acme-review-prompts  1.0.0
kind          prompt
summary       A security lens that knows about our ORM, and a guardrail about migrations

imports       none  (nothing importable — every module is a docstring,
                    so installing it runs nothing)

offers
  (nothing importable to offer — resources only)

evidence
  corpus      2 case(s) — 2 with checks a machine settles, 2 needing a judge
  cassettes   0  — nothing replays offline

digest        sha256:03208834909cadc0bbdde0dcebfb4fb7eac04d0bcbd3a0f4e19c4725c67dfb45

“imports: none” is the line to read first. It means this pack ships no runnable code at all — it is words and example cases. The tool worked that out by reading every file, not by believing a label.

Is it any good?

Measure it against your own cases, for nothing

If a pack ships recordings of real AI answers, you can replay them against your own examples and score it without spending a penny or handing over a key. This one does not, and the tool says so rather than pretending:

in-lockstep pack try
$ in-lockstep pack try acme-review-prompts

acme-review-prompts ships no cassette, so there is nothing to replay
and nothing to measure.

That is a fact about the pack rather than a fault in it: somebody has to
spend real money once, recording what a model actually said, before
everyone after them can measure it for nothing.
Accepting it

You write down what you agreed to

When you accept a pack, the tool re-reads it, records exactly what it found, and hands you the lines to paste. If the pack later contains more than you accepted, that shows up:

in-lockstep add — the end of the output
recorded      .lockstep/packs/acme-review-prompts.json
              commit it: the record IS the acknowledgement.

paste into .lockstep/lockstep.py:

    from in_lockstep.packs import pack

    acme_review_prompts = pack('acme-review-prompts')

until you do, nothing changes: `in-lockstep ls` will not mention
acme-review-prompts.

That last line is the whole safety model in one sentence, printed by the tool itself. Installing offered. Pasting is what accepts.

Part four

Why a plain text file, and not a website

Because the questions that actually matter cannot be answered by a website anyway.

The catalog answers
  • What exists, and roughly what it is for
  • Where to get it, and who published it
  • What the author says it contains
Your machine answers
  • What is really in it — read from the files you downloaded
  • Whether it matches what the catalog claimed
  • Whether it is any good on your examples

So the catalog can be a file in git, reviewed by pull request like everything else, and a company can run its own in an afternoon. There is nothing to host, nothing to log into, and no popularity ranking to game — because the moment you accept a pack, everything worth knowing is worked out again on your side.

And a pack never gets to change how a run behaves by being popular, or by being installed. A project using a pack runs exactly as it would if you had copied the same files in by hand — which is what stops any of this from becoming a way for a stranger's name to end up steering your build.

Being straight about where this is: the tools all work — publishing, cataloguing, searching, checking, measuring, accepting. What does not exist yet is a big public catalog with lots of packs in it. Today this is most useful inside a company, where one team's good review prompt can reach the other forty.

Look at a real one before you build yours.
