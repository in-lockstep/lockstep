See it work

One bug report. Filed to merged. Nobody left GitHub.

A developer types two words in a comment box. Everything after that — which prompt, which guardrails, who is allowed to ask, what it may write, who signs off — is your lifecycle, running in your Actions, answering in the thread.

It is the same back-and-forth a developer already has with an AI on their laptop. The difference is that this one happened somewhere everyone can see, and it is still there next year.

■ gold is a person deciding  ·  ■ mint is the framework working

Part one

Everything happens in the repository you already have

The example: a small team keeps its build steps in acme/build-actions. Someone notices their save action is dropping files.

A person · step 1

You file an issue. Nothing happens.

No bot replies, no workflow fires, no money is spent. An issue is an issue. The framework is not watching your repository — it is waiting to be asked.

The framework · step 3

First it works out whether you were allowed to ask

A chat-ops trigger is an unauthenticated entry point wearing a familiar interface. So the first job holds no credential at all, runs alone, and answers one question: may this person start a run?

job 1 of 3 — no API key, no write token
$ in-lockstep gate --actor dana --association MEMBER

actor     dana
          association=MEMBER
          codeowner=no
          teams-not-checked=1
allowed   dana is MEMBER of this repository

And for somebody who wandered in from the internet:

$ in-lockstep gate --actor drive-by --association NONE

refused   drive-by is NONE and is not named in CODEOWNERS. CODEOWNERS also
          names 1 team(s) (@acme/build-maintainers), and team membership
          cannot be resolved here — it needs a token that can read the
          organisation. Name the person directly, or add them to the
          organisation.

Note what the refusal does not do: quietly pass because it could not check. It says which check it could not perform and what to do about it.

The control: the gate authorises the asker, never the issue. Anyone can write an issue, so the text of one stays untrusted input to a model no matter who typed /fix underneath it. And the trigger matches startsWith rather than contains — otherwise every comment explaining why not to run /fix would run it.
The framework · step 4

The job that talks to the model cannot write. The job that writes never sees the key.

This is the part that is genuinely hard to get right by hand, and it is why the workflow the framework scaffolds has three jobs instead of one.

.github/workflows/fix.yml — the credential split
jobs:
  gate:     permissions: {contents: read}
             — decides who may ask. holds nothing.

  fix:      permissions: {contents: read, issues: read}
             env: ANTHROPIC_API_KEY
             — the model runs here, and cannot write a byte.

  propose:  environment: fix
             permissions: {contents: write, pull-requests: write,
                           issues: write}
             — opens the pull request. never sees the key.
The control: no single process holds both the credential that can spend and the token that can change your repository. The middle job stages its work into a file; the last job picks that file up and re-checks every path in it before writing anything. Put required reviewers on the fix environment and that last job becomes a human approval — in GitHub's own settings, not in a UI this framework invented.
The framework · step 5

It reads your issue — and treats every word of it as hostile

The issue body and every comment on it go into the prompt tagged untrusted, and a scanner reads them on the way past. This is not theoretical: the framework's own runs record injection attempts caught in ticket text.

platform/tickets/base.py
"""Ticket text is untrusted: anyone who can file
   one can write into a prompt."""

items = [ContextItem(kind="ticket",
                     content=f"{key}: {title}\n\n{body}",
                     provenance=UNTRUSTED_EXTERNAL)]

items += [ContextItem(kind="ticket", content=comment,
                      provenance=UNTRUSTED_EXTERNAL)
          for comment in self.comments]

Remember that second block. It is the line that makes step 9 work.

The framework · step 6

It reproduces the bug before it is allowed to fix it

A failing test first, actually run, actually red. Then the fix, and the suite again. A change that never went green stages nothing and opens nothing — the run says so on the issue instead.

The control: this is a step in the lifecycle, not a sentence in a prompt asking the model to please write a test. The framework runs your test command and reads the result. A "fix" for a bug that was never reproduced does not reach a reviewer.
The framework · step 7

It opens a pull request, and answers in the thread

Where the developer was already standing. No email, no dashboard, no notification in a tool half the team has muted.

The framework · step 8

The pull request reviews itself, in the same thread

Opening a pull request in a repository that has in-lockstep fires the review workflow — read-only, one credential, no write token. It leaves one comment and edits that same comment on every later push, so a busy pull request has one review comment rather than nine.

The framework · step 10

Your review is now part of the prompt

Not a setting you changed, not a prompt file you edited. The run fetches the issue and every comment on it, and the conversation on the pull request it opened last time — the thread, the verdict, the notes pinned to a line. Each becomes a piece of context, tagged untrusted and scanned like the rest. That is the loop from step 5 doing its job.

A reviewer's note keeps the line it was written against, because a sentence handed over without its location is an opinion rather than an instruction:

what the second run was given
ticket    #218 (resolved from change request #219)
review    3 remark(s) from #219

context (untrusted)
  @dana reviewed actions/save/action.yml:29 on #219:
  Don't just quote it — `paths` is newline-delimited, so iterate
  the entries. Same as we do in `actions/restore`.

Only pull requests this framework opened are read, matched on the branch it created — so a change request a stranger opened saying "fixes #218" is not gathered as though a reviewer of yours had written it.

The second run opens #220 with the entries iterated, the reproducer still red-then-green, and the same review comment updated in place.

Why this matters more than it looks: the correction is now a durable artifact. It is in the pull request, in the run's record, and readable by the next person who hits the same thing — instead of evaporating in a terminal on one laptop.

The human boundary

Every place a person decides is a place your organisation already has one: the merge button, an environment approval, a CODEOWNERS entry, a label. The framework does not build its own approval UI, because the one you have is the one that is audited.

And afterwards

The whole exchange is still there next year

The thread has what was asked, what was objected to, and what came back. Alongside it, each run appended a record to a branch in your own git: which commit, which model, who approved it, what it decided, how many tokens, how many dollars, and every finding — including the injection signals the scanner caught in the issue text.

And the instructions do not need archiving, because they can be reproduced: show-prompt prints exactly what any run was sent, offline, at any time.

Part two

There are two loops, and one of them you just watched

An agent does not do a job in one reply. It works, checks, and works again until it is done — or until something stops it. Where that loop lives, and what stops it, is the difference between a tool you can put in CI and one you cannot.

In-lockstep has these loops at two heights. The outer one runs between an issue and a merge, and its exit criterion is a person being satisfied. The inner one runs inside a single step of work, and its exit criterion is a test, a schema, or a ceiling. Neither can do the other's job.

The outer loop

Issue → pull request → review → round again. It ends when a person says so.

Part one was the loop. Read it back as one and the shape is obvious: a request goes in, the agent produces work, a human judges it, the judgement becomes part of the next request, and it goes round. What is unusual is only where each turn is written down.

the loop you already watched
  issue #218  a person asks
      │
      ▼
  gated run   who asked? what may it touch? what may it spend?
      │
      ▼
  PR #219     the work, plus a review of the work
      │
      ▼
  a human     reads it. is this what I meant?
      │
      ├── yes ──▶ merge. the loop exits.
      │
      └── no  ──▶ a review on the PR, and /fix there
                    the review becomes context for the next round
                    └──▶ back to the top

The exit criterion here is not a passing test. It is a person being satisfied — the one criterion that genuinely matters and the one you cannot write into a prompt. So the framework does not try to. It makes the round trip cheap, legible and recorded, and leaves the judgement where it was already.

What stops the outer loop: nothing runs between rounds. There is no long-lived agent sitting in your repository waiting for something to do — the default state is stopped, and each round starts only because a person commented again, and is gated and budgeted from scratch when they do. The one place the framework may start a round on its own is a run that failed its own tests: it opens an ai-generated issue, and that path is capped by lockstep.max_attempts (three, by default), counted in labels on the ticket. At the cap it opens nothing and says so: “Automated fix attempts are exhausted (3/3). A human is needed.” doctor fails if those labels do not exist in your tracker — a label silently dropped would leave every attempt reading zero and the cap bounding nothing.
The inner loop · pluggable

The inner loop lives in a strategy, and a strategy is one line you can swap

Step 6 said “it reproduces the bug, then fixes it”, which is one sentence hiding all of the interesting part. That sentence is a strategy, and it is where the inner loop lives.

A verb says what — implement this, fix that. A strategy says how: how many model steps, what runs between them, and what makes it stop. Changing your team's approach is changing one line in the lifecycle file.

.lockstep/lockstep.py
# one model step, no test required — the fast one
lockstep.use(Oneshot)

# or: a failing test first, actually run, before any implementation
lockstep.use(TDD)

# or: yours, with its own ceiling
lockstep.use(DiagnoseThenFix(policy=InvokePolicy(max_turns=8)))

And in-lockstep ls prints Implement -> TDD. The whole answer to “how does implementing happen in this repository” is one line of output, not an archaeology exercise.

Writing your own is subclassing ImplementStrategy (or FixStrategy, or the base for whichever verb). You get the composed prompt, the context, the tools and the invoker; you decide the shape of the work. The framework does not ship one true loop, because the right loop for a one-line typo fix is not the right loop for a migration.

The inner loop · worked example

How the TDD strategy works, and where it refuses

This is not a prompt that asks a model to “do TDD”. A rule stated only in prose is a request, and a model under pressure to finish will write the test and the implementation together and call the result red-then-green without either half having been run.

So the strategy is two model steps with a real test run standing between them — and each step has a way to stop:

implement/tdd — the two phases and their exits
before anything
  no Test verb bound?          -> refuse  tdd.no_test
  rather than quietly degrade to an untested oneshot

phase 1 · red
  "stage a test that fails. only the test."
  agentic loop  model works, calls tools, works again…
  materialise HEAD+test in a throwaway worktree
  run your suite, expect="fail"
    passed / collected nothing / errored
                               -> stop    tdd.not_red

phase 2 · green
  "here is the confirmed-red test. implement it.
   do not edit, weaken, skip or delete it."
  agentic loop
  run your suite, expect="pass"
    still red                  -> stop    tdd.not_green
  no pull request is opened for a change that does not work

then
  revert just the implementation and run again:
  the suite must go red once more
  proof the test depends on the change, and was not
  quietly weakened until it passed

Every one of those exits is a deterministic step the framework ran, not a claim the model made about itself. That is the whole difference.

The inner loop · the turns

Inside a phase: work, check, work again

Each phase hands the model a prompt and a set of tools and lets it go. If it answers, the phase is over. If it asks for a tool, the framework runs the tool, hands back the result, and goes round again. That is the agentic loop, and this is its actual shape:

ai/invoker.py — the turn loop, trimmed
for index in range(policy.max_turns):
    self._guard_turn(policy, started, index)      # kill switch. deadline.

    crossed = self.spend.would_exceed(projected)
    if crossed is not None:
        raise InvocationBlocked("cost.budget_exceeded",
            f"turn {index} would cross the budget;
              refused before the call")

    output = await self.provider.generate(request)

    if not output.tool_calls:
        return Invocation(...)          # it answered. done.

    ... run the tools, append the results, go again ...

return Invocation(..., exhausted=True)   # the cap.
The exit valves

Five ways out, and none of them is “wait and see”

A loop that can only end when the model decides it is finished is a loop that can bill you all night. Every bound below is a ceiling rather than a target, checked by the framework rather than promised by the prompt.

what stops a stuck agent
turn cap       40 for implementing, 1 for a review lens
               a reviewer is handed everything in one prompt;
                an implementer has to go and find it

budget         checked BEFORE each call, against a projection
               so you never pay for the turn that breaks the
                ceiling — it is refused while it is still free

deadline       re-checked every turn, wall clock

kill switch    re-checked every turn — IN_LOCKSTEP_DISABLE

tool results   capped at 20,000 chars each
               a tool result is model input; an unbounded one
                is an unbounded prompt next turn, and the
                history grows quadratically

And an organisation's policy stack can only tighten these. A strategy asking for forty turns under a ceiling of twelve gets twelve; a strategy asking for four gets four. There is no direction in which a policy can loosen an adapter's own bound.

And the honest part

Running out of turns is its own answer — never a quiet pass

When the loop hits the cap, the framework does not hand back the model's last message as though it had finished. The invocation is marked exhausted, and the outcome that carries it is marked as having decided nothing.

adapters/ai/tdd.py
decided=not green_inv.exhausted,
reason="exhausted" if green_inv.exhausted else None,

Two lines, and they are the reason a stuck run cannot be counted as a success anywhere downstream — not on the pull request, not in the run record, not in a future score. “It ran out of room” and “it decided the change was fine” are different sentences, and the framework refuses to blur them.

Why this is the load-bearing bit: anyone can build an agent that loops. The question a team has to answer before putting one in CI is what happens on the bad day — and “it stops, it says which bound it hit, and it does not claim to have succeeded” is a much easier thing to sign off than a promise about how well the prompt was written.

Part three

Or keep hacking on your laptop — it still gets written down

Nobody wants to file an issue to try something. The same verbs run from a terminal, against the same lifecycle file, with the same guardrails and the same ceilings.

the same run, on a laptop
$ in-lockstep run fix/from-ticket --arg ticket='#218' --approve --budget 2.00

staged    reproducer + fix -> .lockstep/artifacts/fix-changeset
fix       succeeded
ledger    lockstep-history:records/fix-from-ticket-…json

Same workflow id as the one CI runs. The trigger, the job split and the credentials are what CI owns; the lifecycle is Python you can put a breakpoint in.

What is different is only where the approval came from: --approve from a person at a keyboard, a verified trigger in CI. What is the same is everything worth keeping — the same prompt, the same guardrails, and a record appended to the history branch either way.

Which means a developer exploring on their own machine is not working outside the process. They are producing the same evidence as everyone else, and any run can be replayed later with --offline for nothing.

Not built yet, and worth being clear about. Those records are the raw material for a learning loop: harvest what happened, turn it into cases, and test a proposed change to a prompt or a guardrail against real history before anyone pays for it. Today you can see exactly what a change does to a prompt (show-prompt --diff) and score cases you write yourself. Harvesting history into those cases automatically is designed and not implemented. It is the reason the records are being kept in this shape now.

A run failed and filed its own bug report. A person put a label on it. An agent fixed it and opened a pull request. A person merged it. Neither side did the other's job — which is where the name comes from.
