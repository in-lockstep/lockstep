See it work

Set it up in four commands. Then watch one change go all the way through.

A real Python library — tempo, which parses duration strings — adds in-lockstep to itself, and then one feature travels from a rough idea to a merged pull request. At every step you can see what the AI was told, what it did, and where a person had to decide. Every black block below is real output, not a mock-up.

Part one

Setting it up: four commands and one file you own

Nothing to sign up for, nothing to host, and nothing to configure before the first run works.

Step 1 · install

Add it like any other dependency

One distribution. Provider SDKs are extras, so a bare install pulls none of them — cold start matters in CI.

tempo — a small Python library, 4 files, 4 tests
$ uv add in-lockstep
Step 2 · init

It reads your project before it writes anything

No questionnaire, no wizard. It looks at what is already there and scaffolds a lifecycle that binds the tools you actually use.

detection, then two files
$ in-lockstep init

wrote .lockstep/lockstep.py
  detected stack: python; tests: pytest; lint: ruff; Makefile (check)
wrote .github/workflows/lockstep.yml

One job, because reviewing is read-only. Add the privileged `apply` job the
day a verb of yours produces a change to write; the file says where.

It found pytest and ruff and wrote the bindings for them. It also noticed there is nothing here that writes yet, and scaffolded the CI file accordingly — one job, not two.

The file it wrote is thirty lines and it is yours. This is the whole of it that matters:

.lockstep/lockstep.py
from in_lockstep import Lockstep
from in_lockstep.adapters import PytestTest, RuffValidate, Test, Validate
from in_lockstep.middleware import CostBudget, otel

lockstep = Lockstep.detect()

lockstep.bind(Test, PytestTest(args=["-q"]))
lockstep.bind(Validate, RuffValidate())

lockstep.middleware += [otel(), CostBudget(usd=2.00)]

Executable Python, not a manifest. Your lifecycle is a module that runs — so it diffs, it reviews, it has blame, and you can put a breakpoint in it.

Step 5 · make it yours

Adding a house rule is a diff, not a support ticket

Every team has a rule the shipped prompts do not know about. Ours: do not widen the grammar without a test for the new unit. One file, one line of binding — and then the framework will show you exactly what changed about what the model is told.

what your guardrail actually did to the prompt
$ in-lockstep show-prompt security --diff

--- shipped/review/security
+++ AiReview/review/security
@@ -42,6 +42,10 @@
+<!-- guardrail: tempo/house -->
+Never propose a change to `src/tempo/parse.py` that widens the grammar without
+a test for every new unit. The grammar is the whole library; an untested unit
+is a silent parse failure downstream.

Four lines, reviewable, in the diff of the pull request that added them. plus() appends — a house rule lands after the shipped baseline and cannot displace it.

And ls keeps score, so nobody has to remember which prompts a team has customised:

in-lockstep ls
prompts  (what each AI binding composes; * = not the shipped prompt)
  AiReview           review/intent review/performance review/security review/tests
                     guardrails: baseline, review/reviewing, tempo/house

Part two

One change, start to finish

The feature: tempo should understand weeks, so 2w means 1,209,600 seconds. This is the part that is hard to standardise by hand — which step uses AI, what it is told, what it is not allowed to do, and where a person has to sign off. Green is the framework working. Gold is a person deciding.

Stage 1 · rfe

A rough idea becomes a ticket somebody can argue with

You have a sentence. The framework turns it into a draft with a problem statement and acceptance criteria — and then stops.

drafted, and deliberately not filed
$ in-lockstep rfe --idea "tempo should understand weeks, so 2w parses as 1209600"

rfe       succeeded

not filed. Read it, then re-run with --create to file it — or edit and
file it yourself.
A person decides

Nothing reaches your tracker without a human

The human boundary

The draft is printed, not filed. --create is a second command a person runs after reading it. The framework's position is that the human acts in the system of record — the tracker, the pull request, the environment approval — never in a bespoke UI it invented.

Stage 2 · triage

Classify it before anyone expensive looks at it

What kind of work is this, how urgent, what is missing from the description. Cheap enough to route to a local model — triage on local:qwen3-8b costs exactly nothing and still counts its tokens.

A person decides

The first thing the framework does is refuse

Ask it to implement, and it stops — because nothing in this lifecycle yet says how a human stays in the loop.

a startup refusal, with the fix
$ in-lockstep implement --ticket-file weeks.md --strategy tdd

Error: TDD lets a model write or execute, and no ApprovalGate is in the
middleware chain. Add one:

    lockstep.middleware += [ApprovalGate()]

The human acts in your system of record — a review request, an environment
approval — so the gate refuses without a grant rather than prompting.

Before the first model call, before a cent is spent. The refusal names the line to paste, and explains why it would rather refuse than ask you a question in a terminal nobody is watching at 2am.

You add one line

That line is a diff, in a file loaded from a trusted ref, reviewed like any other code. Which is the point: the thing that grants an agent its authority is itself under review.

Stage 3 · implement, test-first

Red, then green — enforced by the strategy, not asked for in a prompt

The TDD strategy runs in two model steps with a real test run between them. It asks for a failing test, materialises that test in a throwaway worktree and runs your suite to confirm it is red, then asks for the implementation and runs the suite again to confirm green.

A test that passes before anything was written stops the run (tdd.not_red) — because a test that was already green tested nothing. An implementation that leaves it failing comes back tdd.not_green rather than opening a pull request that does not work.

The control: the strategy will not proceed without a red test first. Not a prompt asking nicely — a `Test` verb it actually ran.
Stage 4 · staging

The model writes nothing to your tree

A session stages its work into a ChangeSet and touches nothing. Applying it is a separate step that re-runs the path guard on the artifact.

The control: in CI those are two jobs — and only the second holds a write token. The job that talks to the model has contents: read and no ability to write; the job that opens the change never sees the provider credential. One process cannot hold both.
Stage 5 · review

Four lenses, each an agent rather than a checklist row

Security, intent, performance, tests — separately promptable, separately budgetable, separately measurable. Here is the security lens on a real merged pull request, replayed offline:

A person decides

It opens as a draft, and it says so

Draft until the tests actually pass

An AI-authored change opens as a draft pull request, and is marked ready only when the suite passed against the staged change. If it did not, the run files a follow-up issue instead — and the comment it leaves says, in as many words, “Nobody has read it yet.”

Your reviewers keep the last word, and the tool never pretends otherwise.

Stage 6 · when it fails

A failed run becomes a ticket, not a silence

If the suite goes red, the run opens an ai-generated issue describing what it tried — which an agent may pick up and attempt again.

The control: the loop is bounded. Attempts are capped, the count lives in labels on the ticket, and doctor fails if those labels do not exist — because a tracker that silently drops an unknown label would leave every follow-up reading attempt zero and the cap bounding nothing.
Stage 7 · backport

Deterministic first; a model only where one is needed

Replaying a merged change onto a release line is git cherry-pick -x in a throwaway worktree — no model, no cost, no risk. A model is invited only for the conflicted paths, only with --resolve, and only inside the same budget and approval gates as everything else.
