See it work

One bug report. Filed to merged. Nobody left GitHub.

A developer types two words in a comment box. Everything after that — what the AI is told, who is allowed to ask, what it may change, who signs off — is your own setup, running in your own build, answering in the thread.

It is the same back-and-forth a developer already has with an AI on their laptop. The difference is that this one happened somewhere everyone can see, and it is still there next year.

■ gold is a person deciding  ·  ■ mint is the framework working

Part one

Everything happens in the repository you already have

The example: a small team keeps their build scripts in acme/build-actions. Someone notices files going missing.

A person · step 1

You file an issue. Nothing happens.

No bot replies, nothing runs, nothing is spent. An issue is just an issue. The framework is not watching your repository — it is waiting to be asked.

You type two words

In the comment box every developer on the team already uses. There is nothing to install in an editor, no separate console to learn, and no second place where the conversation lives.

The framework · step 3

First it checks that you were allowed to ask

Anyone who can see the repository can type a comment in it. So the very first thing that runs has no password of any kind, does nothing else, and answers one question: is this person allowed to start a run?

step 1 of 3 — no AI key, no ability to change anything
$ in-lockstep gate --actor dana --association MEMBER

actor     dana
          association=MEMBER
          codeowner=no
          teams-not-checked=1
allowed   dana is MEMBER of this repository

And for somebody who wandered in from the internet:

$ in-lockstep gate --actor drive-by --association NONE

refused   drive-by is NONE and is not named in CODEOWNERS. CODEOWNERS also
          names 1 team(s) (@acme/build-maintainers), and team membership
          cannot be resolved here — it needs a token that can read the
          organisation. Name the person directly, or add them to the
          organisation.

Notice what the refusal does not do — shrug and let it through because it could not check. It says which check it could not make, and what to do about that.

Worth knowing: this checks the person, not the issue. Anyone can write an issue, so the words in one are always treated as something that might be trying to trick the AI — no matter who asked for the run underneath it.
The framework · step 4

The part that talks to the AI cannot change your code

And the part that changes your code never sees the AI key. That is why the setup has three steps rather than one — it is easy to get wrong by hand, so the framework writes it for you.

.github/workflows/fix.yml — who is allowed to do what
jobs:
  gate:     permissions: {contents: read}
             — decides who may ask. holds nothing.

  fix:      permissions: {contents: read, issues: read}
             env: ANTHROPIC_API_KEY
             — the model runs here, and cannot write a byte.

  propose:  environment: fix
             permissions: {contents: write, pull-requests: write,
                           issues: write}
             — opens the pull request. never sees the key.
Why it is split: nothing ever holds both the key that spends money and the permission to change your code. The middle step writes its work to a file; the last step picks that file up and re-checks every path in it before touching anything. Add required reviewers to that last step in your GitHub settings and it becomes a human sign-off — in the settings you already have, not somewhere new.
The framework · step 5

It reads your issue — and assumes it might be a trap

The issue and every comment on it get handed to the AI marked untrusted, and something checks them on the way past for attempts to give the AI instructions of their own. This is not hypothetical — this project's own runs have caught them in real issue text.

platform/tickets/base.py
"""Ticket text is untrusted: anyone who can file
   one can write into a prompt."""

items = [ContextItem(kind="ticket",
                     content=f"{key}: {title}\n\n{body}",
                     provenance=UNTRUSTED_EXTERNAL)]

items += [ContextItem(kind="ticket", content=comment,
                      provenance=UNTRUSTED_EXTERNAL)
          for comment in self.comments]

Remember the second half — every comment, not just the issue. That is the bit that makes step 9 work.

The framework · step 6

It proves the bug is real before it is allowed to fix it

First it writes a test that fails because of the bug, and actually runs it to watch it fail. Then it fixes the code and runs your tests again. If they do not pass, nothing gets proposed at all — the run says so on the issue instead.

Why this beats asking nicely: the framework runs your test command itself and reads the result. It is not a line in a prompt requesting that the AI please write a test. A "fix" for a bug nobody ever reproduced does not reach a reviewer.
The framework · step 7

It opens a pull request, and answers in the thread

Where the developer was already standing. No email, no dashboard, no notification in a tool half the team has muted.

Worth knowing: a fix only arrives ready for review because its test failed first and passes now. Work without that proof opens as a draft instead. And if the tests actually failed, the run opens a follow-up issue rather than a pull request — with a hard cap on how many times it will try again.
The framework · step 8

The pull request reviews itself, in the same thread

Opening a pull request starts the review. It can read your code and nothing else. It leaves one comment and edits that same comment every time you push again — so a busy pull request has one review to read, not nine.

The framework · step 10

Your review is now part of what the AI is told

You did not change a setting or edit a file. The run reads the issue, every comment on it, and the whole conversation on the pull request it opened last time. All of it is handed over marked untrusted and checked, exactly as in step five.

Your note keeps the line it was written against, because "iterate the entries" without a location is an opinion, and with one it is an instruction:

what the second run was given
ticket    #218 (resolved from change request #219)
review    3 remark(s) from #219

context (untrusted)
  @dana reviewed actions/save/action.yml:29 on #219:
  Don't just quote it — `paths` is newline-delimited, so iterate
  the entries. Same as we do in `actions/restore`.

Only pull requests the framework opened itself are read. Somebody opening their own pull request that mentions #218 does not get their opinions fed to your agent.

The second run opens #220 with the entries iterated, the reproducer still red-then-green, and the same review comment updated in place.

Why this matters more than it looks: the correction is now kept. It is in the pull request and in the run's record, where the next person to hit the same thing can read it — instead of vanishing from a terminal on one laptop.

The human boundary

Every point where a person decides is one your company already had: the merge button, a required approval, a code-owners list, a label. The framework builds no approval screen of its own, because the one you already use is the one that gets audited.

And afterwards

The whole exchange is still there next year

The thread holds what was asked, what was objected to, and what came back. Beside it, every run wrote a record into your own git history: which commit, which model, who approved it, what it decided, how many tokens and how many dollars.

The instructions themselves do not need storing, because they can be reproduced. One command prints exactly what any run was sent — offline, any time, free.

Part two

There are two loops, and one of them you just watched

An AI agent does not finish a job in one reply. It works, checks its own result, and goes again — until it is done, or until something stops it. Knowing what stops it is the difference between a tool you would put in your build and one you would not.

There are two of these loops here. The big one runs from an issue to a merge, and it ends when a person is happy. The small one runs inside a single piece of work, and it ends when a test passes or a limit is hit. Neither can do the other's job.

The big loop

Issue, pull request, review, round again — until a person says stop

Part one was this loop. Read it back and the shape is obvious: somebody asks, the agent produces something, a person judges it, that judgement feeds the next attempt, and round it goes. The only unusual part is that every turn is written down.

the loop you already watched
  issue #218  a person asks
      │
      ▼
  gated run   who asked? what may it touch? what may it spend?
      │
      ▼
  PR #219     the work, plus a review of the work
      │
      ▼
  a human     reads it. is this what I meant?
      │
      ├── yes ──▶ merge. the loop exits.
      │
      └── no  ──▶ a review on the PR, and /fix there
                    the review becomes context for the next round
                    └──▶ back to the top

What ends this loop is not a passing test. It is a person being satisfied — the thing that actually matters, and the thing you cannot write down as a rule. So the framework does not try. It makes each lap cheap, readable and recorded, and leaves the judging to the people who were already doing it.

What stops it: nothing runs in between. There is no agent sitting in your repository waiting for something to do — it is switched off by default, and a round only starts because somebody commented again. The one time the framework starts a round by itself is when a run fails its own tests: it files a follow-up issue, and gives up after three tries, saying so plainly — “Automated fix attempts are exhausted (3/3). A human is needed.”
The small loop · swappable

How the work gets done is one line you can change

Step 6 said “it proves the bug is real, then fixes it”. That one sentence hides all the interesting part — and it is a choice, not a fixed behaviour.

The job says what: fix this, build that. The approach says how: how many times the AI is asked, what runs in between, and what makes it stop. Switching approach is one line:

.lockstep/lockstep.py
# one model step, no test required — the fast one
lockstep.use(Oneshot)

# or: a failing test first, actually run, before any implementation
lockstep.use(TDD)

# or: yours, with its own ceiling
lockstep.use(DiagnoseThenFix(policy=InvokePolicy(max_turns=8)))

And one command prints which one is in use. "How does this repository build things?" is a line of output rather than an afternoon of reading.

Writing your own is writing a small Python class. You are handed the instructions, the context and the tools, and you decide the shape of the work. There is no single built-in loop, because the right approach for a one-line typo is not the right approach for a migration.

The small loop · an example

Test-first, and the four places it refuses

This is not a prompt asking the AI to please work test-first. A rule written only in words is a request — and an AI under pressure to finish will write the test and the fix together and report success without either having been run.

So the approach is two goes at the AI with a real test run in between, and each stage has a way to stop:

implement/tdd — the two phases and their exits
before anything
  no Test verb bound?          -> refuse  tdd.no_test
  rather than quietly degrade to an untested oneshot

phase 1 · red
  "stage a test that fails. only the test."
  agentic loop  model works, calls tools, works again…
  materialise HEAD+test in a throwaway worktree
  run your suite, expect="fail"
    passed / collected nothing / errored
                               -> stop    tdd.not_red

phase 2 · green
  "here is the confirmed-red test. implement it.
   do not edit, weaken, skip or delete it."
  agentic loop
  run your suite, expect="pass"
    still red                  -> stop    tdd.not_green
  no pull request is opened for a change that does not work

then
  revert just the implementation and run again:
  the suite must go red once more
  proof the test depends on the change, and was not
  quietly weakened until it passed

Every one of those exits is something the framework ran and checked — not something the AI said about its own work. That is the whole difference.

The small loop · one go

Inside one go: work, check, work again

The AI is handed the instructions and a set of tools, and let loose. If it answers, that go is over. If it asks to use a tool, the framework runs the tool, hands back the result, and round it goes. That is the loop, and this is what it really looks like:

ai/invoker.py — the turn loop, trimmed
for index in range(policy.max_turns):
    self._guard_turn(policy, started, index)      # kill switch. deadline.

    crossed = self.spend.would_exceed(projected)
    if crossed is not None:
        raise InvocationBlocked("cost.budget_exceeded",
            f"turn {index} would cross the budget;
              refused before the call")

    output = await self.provider.generate(request)

    if not output.tool_calls:
        return Invocation(...)          # it answered. done.

    ... run the tools, append the results, go again ...

return Invocation(..., exhausted=True)   # the cap.
The exit valves

Five ways out, and none of them is “hope it stops”

A loop that ends only when the AI decides it is finished is a loop that can bill you all night. Each limit below is a ceiling, not a target, and the framework checks it rather than asking the AI to respect it.

what stops a stuck agent
turn cap       40 for implementing, 1 for a review lens
               a reviewer is handed everything in one prompt;
                an implementer has to go and find it

budget         checked BEFORE each call, against a projection
               so you never pay for the turn that breaks the
                ceiling — it is refused while it is still free

deadline       re-checked every turn, wall clock

kill switch    re-checked every turn — IN_LOCKSTEP_DISABLE

tool results   capped at 20,000 chars each
               a tool result is model input; an unbounded one
                is an unbounded prompt next turn, and the
                history grows quadratically

And your company's rules can only make these stricter. An approach asking for forty goes, under a company limit of twelve, gets twelve. There is no direction in which a rule can loosen one of these.

And the honest part

Running out of room is its own answer — never a quiet pass

When the loop hits its limit, the framework does not hand back the AI's last message as though it had finished. The run is marked as having decided nothing:

adapters/ai/tdd.py
decided=not green_inv.exhausted,
reason="exhausted" if green_inv.exhausted else None,

Two lines, and they are why a stuck run can never be counted as a success — not on the pull request, not in the record, not in any later score. “It ran out of room” and “it decided the change was fine” are different sentences, and the framework will not blur them.

Why this is the part that matters: anyone can build an agent that loops. The question you have to answer before putting one in your build is what happens on a bad day — and “it stops, it says which limit it hit, and it does not claim to have succeeded” is a far easier thing to sign off than a promise about prompt quality.

Part three

Or keep hacking on your laptop — it still gets written down

Nobody wants to file an issue just to try something. The same commands run from a terminal, against the same setup file, with the same rules and the same limits.

the same run, on a laptop
$ in-lockstep run fix/from-ticket --arg ticket='#218' --approve --budget 2.00

staged    reproducer + fix -> .lockstep/artifacts/fix-changeset
fix       succeeded
ledger    lockstep-history:records/fix-from-ticket-…json

Exactly the same thing your build runs. Your build owns the trigger and who holds which key; the rest is ordinary Python you can step through in a debugger.

The only difference is where the go-ahead came from: you typed it, or a checked trigger supplied it. Everything worth keeping is the same — the same instructions, the same rules, and a record written to your git history either way.

So a developer trying things on their own laptop is not working outside the process. They are leaving the same evidence as everyone else, and any run can be replayed later for nothing.

And those recordings turn into tests

This is why the records are kept in the shape they are. One command reads a recording and writes out test cases — real questions that were really asked, with the real answers that came back:

history becoming something you can check
$ in-lockstep eval harvest --from .lockstep/cassettes/review.json --family review

wrote  corpus/review/review-this-diff-for-security-problems.json

1 case(s) from .lockstep/cassettes/review.json

The case it wrote expects what the AI actually said: two findings, and the exact wording of each. Nobody typed any of that.

$ in-lockstep eval run

  ok      review-this-diff-for-security-problems

cases        1 replayed, 0 skipped
decided      1
pass rate    100%

Free, and it takes under a second. Break something in how answers get read, and it goes red with the specific check that broke:

  FAIL    review-this-diff-for-security-problems
          contains: 'Session outlives the request and leaks a connection'
          count.findings: expected 2, got 1

So the pile of recordings stops being a pile. Every real run your team does becomes a test of the situations your team actually hits — not the ones somebody imagined while writing an example suite.

What this checks, and what it doesn't. Replaying is free, and it tests everything around the AI — how its answer gets read, parsed and turned into a result. That breaks silently and now it can't. Testing a change to the AI's instructions is a different thing: same recorded question, new answer, so it is a real call and costs real money. What was missing was never the willingness to pay for that — it was having anything to compare the result against.

A run failed and filed its own bug report. A person put a label on it. An agent fixed it and opened a pull request. A person merged it. Neither side did the other's job — which is where the name comes from.
