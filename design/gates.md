# in-lockstep exit gates

Every gate referenced by id in the pivot plan, defined here. A gate named in a phase table and
defined nowhere is indistinguishable from a gate that does not exist. That was the weak point of
two review rounds (R6-QA-5), so this file is a Phase-0 deliverable and the phase tables reference
it rather than restating it.

`(Pn)` is the phase whose exit the gate blocks. `(Pn-m)` means it holds continuously across a range.

`design/objectives.md` is the ledger one level up, and it reads this file. Each of the ten
objectives in `CLAUDE.md` names the gates that carry it and the gates it is blocked on, and
`GATE-TEST-8` fails when the two files disagree — so a gate here changing status is a gate that
has to be accounted for there. That join is why an `unmet` row is worth writing before anybody
intends to implement it: it is how a gap becomes something an objective can point at, instead of
prose in a review nobody re-reads.

## Status, and why this column exists

The preamble above says a gate defined nowhere is indistinguishable from one that does not exist.
The same argument runs one step further, and this file did not make it: **a gate that is defined,
and whose mechanism is unit-tested, and which nothing invokes during a run, is also
indistinguishable from one that does not exist.** Nine rows below were in that state while
`docs/controls-crosswalk.md` cited them as evidence that a substrate control had been replaced.

| Status | Meaning |
|---|---|
| `held` | The mechanism runs on a live path and an assertion covers it. |
| `unit only` | The mechanism exists and is tested in isolation. Nothing calls it during a run, so the assertion, which is about a run, is not established. **Not a pass.** |
| `partial` | Some clause of the assertion is covered and some is not; the row says which. |
| `unmet` | No mechanism, or a mechanism with nothing asserting over it. |
| `deferred` | Past the 1.0 cut line, by the deferral recorded at §17.11 of `design/in-lockstep-design.md` — which names `ctx.park` and `ctx.fan_out` as not on `RunContext` at 1.0, and is what every `deferred` row here rests on. |
| `retired` | The subject was deleted; the row records what it held and why it stopped. |

`unit only` is the status worth understanding, and `GATE-EGRESS-1` was the example. It had a
thorough test that a `ContextPackage` carrying untrusted content under `EgressMode.NONE` raises
`EgressRefused`. That is a real test of a real mechanism. But `EgressPolicy.check()` had no
caller outside that test, so no run had ever been refused and the gate's actual assertion
("BLOCKED before the first model call") had never been exercised. It is `held` now, because
`AiInvoker.run` calls it.

The distinction this project already draws between `decided` and `succeeded` is the same one: a
mechanism nobody invoked is outstanding, not passed.

No row is in that state now — `GATE-LEDGER-2` was, until PR-18 gave `compare()` its caller; `GATE-RETRY-5` stood beside it until #265 retired it with its subject — and `GATE-OUT-2` was `partial` beside it until #267 struck the two clauses that named a `Cache`
nobody wrote. Each row says what is missing. `GATE-EVIDENCE-1` stood beside it until #268 promoted the first case; its row
says what one promotion does and does not establish.

They were found by re-checking every `held` row for a call site, which is the exercise the column
was created by and had not been repeated since; 5 of 69 did not survive it. Four of the five were
wrong about nothing but their own status. The fifth, `GATE-EVAL-1`, also gave a reason that was
never true here — it credited a progressive-disclosure hole that this codebase does not have — and
that went unnoticed for the same reason the status did: a row over a mechanism nobody calls is a
row nobody has occasion to check. Two of those five — `GATE-LEDGER-4` and
`GATE-EVAL-1`, both over `EvalSubject` — are `held` again, because a run now computes a subject and
the record keeps it. That round trip is what the column is for: the rows said `unit only` for
exactly as long as it was true, and moving them back cost a call site rather than an edit.

The pair named here before was `GATE-APPROVAL-1` and `GATE-POLICY-1`. Both are `held` now, and this
sentence went on naming them anyway — the decay described one paragraph up, arriving in the
paragraph that describes it. A status column nobody re-checks is what this file is about, and so is
a sentence about one.

Nothing enforced this file's *primary key* either, until `GATE-TEST-7`. `GATE-EVAL-1` named two
unrelated properties from #136 until #213, and because `test_gates.py` searches the test tree as one
concatenated string, each row was discharged by the other's test: delete either test and both rows
stay green. The unmet half of the ratchet is worse under a duplicate — an id some unrelated test
already cites can never be marked `unmet`, so the only status it can carry is a reassuring one.
